# #59-01 反事实重放：数据可行性结论

日期：2026-10-26 · 结论：**不做**（没有可信的反事实压缩模型）

## 查了什么

- ZCode `~/.zcode/cli/db/db.sqlite`
  - `turn_usage`：2939 行，按“用户轮次”聚合，`input_tokens` 是一轮内多次
    模型请求的总和（本机样本单轮可达 392M），不是单次上下文大小。
  - `model_usage`：52783 行，有单次请求的 `input_tokens`；但同一会话内
    并行/重试/侧链请求混在一起，56 次“>50% 下跌”里包含大量并行分支和
    新请求，不是可归因的压缩事件。
- Claude Code `~/.claude/projects/**/*.jsonl`：122 个文件、6726 条 assistant
  usage；有 input/cache_read/cache_creation，但**没有压缩标记**
  （`isCompactSidechain` 在本机样本中 0 命中）。64 次大下跌可被同秒
  并行 assistant 消息解释，不能当成压缩点。
- Codex `~/.codex/sessions`：392MB，有 per-turn token 记录，但没有
  “压缩前/压缩后”的成对上下文，也没有 compact 事件标记。
- cc-switch `proxy_request_logs`：24671 行 per-request token，适合做实际
  花费/缓存分析，但不记录“未压缩会怎样”。

## 为什么不做

“若在 T 压缩，省多少”需要同一会话在**同一时刻**的压缩/未压缩两条轨迹。
本机日志只有实际发生的一条；用实际压缩后的降幅去外推更早的压缩点，会把
并行请求、缓存命中、侧链和模型行为混在一起，得到看似精确但不可复核的
数字。`#59` 的风险节也明确要求数字必须手算可复核。

## 建议

- 保留已完成的 #59-02（百分比反推）与 #59-03（parser_rev）。
- 如果以后需要“压缩洞察”，只做**观察式**指标：某次实际上下文下降前后
  的 token 差值，明确标“观察值，不是反事实”，并先在本地会话列表做
  可复核样本；不要用“若在 T 压缩省 $X”的推演文案。
