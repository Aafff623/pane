# 刷新机制表达层升级：静默新鲜化 + 失败分级

**Status:** ready-for-agent
**Feature dir:** `.scratch/refresh-ux/`
**Date:** 2026-10-12
**来源:** 用户看到「⚠ 数据过时」后质疑机制；确认方向=静默新鲜化 + 失败分级（2026-10-12）

## Problem Statement

刷新机制骨架（缓存先上屏+后台重请求+失败沿用）已是主流形态，但**表达方式**把正常状态说成了故障：

1. **开机首屏**：磁盘缓存快照全部标 ⚠ 数据过时——那是"预热"不是"故障"，却用警告语义。
2. **失败一次就 ⚠**：3 分钟宽限后任何一次失败都亮警告，没有"连续失败才升级"的概念。
3. **降级态无行动入口**：亮 ⚠ 后用户只能等下一拍或找全局刷新，卡片上没有重试。
4. **新鲜度不可见**：健康状态下用户不知道数据几岁（中性信息缺位）。

## Solution

- 开机缓存改用**中性表达**（"缓存数据 · 刷新中"），不再用 ⚠。
- ⚠ 升级为真正的**降级态**：同一 provider **连续 2 次拉取失败**才亮（3 分钟静默宽限不变），悬浮保留具体原因，**点击 ⚠ 即重试该卡**。
- 底部加**中性新鲜度**："数据更新于 X 分钟前"（始终显示，无配置键）。
- 轮询节奏加 **±10% 抖动**（对齐主流退避实践；15 秒断网重试保持固定）。

## User Stories

1. As a 用户, I want 开机看到的是"缓存数据·刷新中"而不是一排警告, so that 正常启动不被误读为故障
2. As a 用户, I want 只在连续失败时才看到 ⚠, so that 偶发网络抖动不制造焦虑
3. As a 用户, I want 点一下 ⚠ 就重试这张卡, so that 恢复不需要寻找全局刷新
4. As a 用户, I want 随时看到"X 分钟前更新", so that 我知道数据多新鲜而不需要警告来暗示
5. As a 用户, I want 多家 provider 的刷新节奏有抖动, so that 请求不同时砸向同一个限流网关

## Implementation Decisions

- `Snapshot` 增加可选 `boot_cache` 标记（serde 默认 false，旧缓存文件兼容）；`cached_usage` 置位；前端对 boot_cache 渲染中性 chip，对 stale 渲染 ⚠。
- Rust 维护每卡**连续失败计数**（按快照 id）：本次失败（error 或降级透传）+1、成功清零；restore 的 stale 判定从"超宽限即标"改为"超宽限**且**连续 ≥2 次"。
- ⚠ chip 复用现有单卡刷新事件（data-card-refresh），变可点击；悬浮原因保留。
- 底部状态行在空闲时显示"数据更新于 X 分钟前"（前端 lastFetch，可见定时器每分钟刷新文案）；不加配置键——中性信息无需开关（偏离原提案"设置可关"，理由：配置键要动四处+设置面板，价值不成比例）。
- 主循环睡眠时长乘 0.9–1.1 抖动因子（rand_core 已在依赖）。

## Testing Decisions

- 连续失败计数的判定逻辑做成纯函数进 parse-tests（升到阈值才标 stale、成功清零、降级透传计数）。
- boot_cache serde 兼容（旧缓存无此字段）由现有反序列化路径覆盖。
- 表达层（chip 文案/可点击/底栏）走 tsc/vite + 用户 UI 验收。

## Out of Scope

- 刷新间隔、3 分钟宽限、24 小时缓存上限等既有参数不变。
- 设置面板不加开关。
- 按 provider 的差异化节奏（本期只做全局抖动）。

## Further Notes

- 用户拍板（2026-10-12）：方向认、可选项全要。
- 命名沿用现状词汇：stale=降级、boot_cache=开机预热，不引入新领域词。
